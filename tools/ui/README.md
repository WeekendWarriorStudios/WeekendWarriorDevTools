# Dev Tools UI

A local, browser-based tile grid for every tool under `tools/`: click a tool, fill in its
parameters, read what it does, hit Run, and watch its output live. New tools dropped into
`tools/` show up automatically — no registry file to hand-edit.

```
tools/ui/
├── scan_tools.py            # canonical scanner (AST-based) - used by server.py directly
├── Scan-Tools.ps1           # equivalent scanner (regex-based), for a pure-PowerShell context
├── server.py                # local web server: serves web/, runs tools, streams output
├── Launch-DevToolsUI.ps1    # convenience: finds Python, starts server.py, opens a browser
├── web/                     # the page itself (static HTML/CSS/JS, no build step)
└── manifest.json            # generated by a scan - gitignored, never hand-edited
```

## Running it

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui\Launch-DevToolsUI.ps1
```

or directly:

```powershell
python tools\ui\server.py
```

Opens `http://127.0.0.1:8756/` in your browser. Stop with Ctrl+C.

## How discovery works

`scan_tools.py` walks `tools/` for `.ps1` and `.py` files and statically parses each one - it
never imports or executes a script, only reads its source - so scanning is safe even for tools
that mutate the project or only work inside a running editor. The server re-scans once at
startup and again whenever the page loads or you click **Rescan**; it never scans on a timer.

Three "kinds" come out of a scan, matching the main README's execution-context table:

| Kind | What it means | How the UI runs it |
|---|---|---|
| `powershell` | any `.ps1` | `powershell -File <script> -Param value ...` |
| `python-cli` | a `.py` that builds an `argparse.ArgumentParser` | `python <script> --flag value ...` |
| `python-editor` | a `.py` that `import unreal`s - no argv parsing, meant to be imported and have one function called | generates a small loader snippet and runs it via `ue_remote_exec.py --file`, which requires the Unreal Editor to be open with **Python Remote Execution** enabled |

For `python-editor` tools, the scanner has to guess which function is the "entry point" (the
file has no CLI to declare one). It looks, in order, for: a zero-argument `main()`; a bare
function call inside `if __name__ == "__main__":` (and pulls that call's literal arguments in as
example values); a function named in the module docstring's own usage example; and only then
falls back to guessing from the signature. If it guessed, the tool's detail panel shows a note
and a dropdown to pick a different function - the guess is never silent.

A tool's parameter defaults are read from its actual source (a PS1 `param()` block, an argparse
`add_argument()` call, or a Python function signature) - including simple module-level constant
references (`default=DEFAULT_HOST`) resolved back to their literal value. A default the scanner
can't reduce to a plain value (an f-string built from other constants, a `Join-Path` call) is
shown as a placeholder rather than guessed at.

## Command construction & safety

The server builds each command from the manifest's own parsed parameter list - it never
evaluates freeform text from the page as code. PowerShell arguments are passed as properly
quoted PowerShell literals (so array/switch parameters work correctly); Python CLI arguments are
passed as a plain argv list (no shell involved, so there's no quoting/injection surface); a
`python-editor` call is rendered as `repr()`-safe keyword arguments into a tiny generated script
that loads the target file by path (sidestepping hyphenated filenames like
`validate-asset-data.py`, which can't be `import`ed by name) and calls the chosen function. The
exact resolved command is always shown in the UI before/while it runs.

Running a tool is still running it: a script that deletes, renames, or writes files will still
do so from this UI exactly as it would from a terminal. Nothing here adds a safety net beyond
what the script itself already has (`-DryRun`, confirmation prompts, etc.) - use those the same
way you would on the command line.

## Re-scanning manually

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\ui\Scan-Tools.ps1 -OutputPath tools\ui\manifest.json
python tools\ui\scan_tools.py --pretty --out tools\ui\manifest.json
```

`Scan-Tools.ps1` is a best-effort, regex-based standalone equivalent for a context with no
Python available; the server always uses `scan_tools.py`'s AST-based parser, which is the more
precise of the two (in particular for `python-editor` entry-function detection). Both write the
same manifest shape, so either can be inspected on its own without starting the server.
